# legacy — ιστορικό, όχι εκτελέσιμη ακολουθία

**Τίποτα εδώ δεν τρέχει.** Ο runner διαβάζει μόνο το `db/migrations/*.sql`.

Αυτά τα αρχεία ήταν η παλιά ακολουθία, πριν την ενοποίηση. Διατηρούνται γιατί
εξηγούν **πώς φτάσαμε στο σημερινό σχήμα** — αλλά το σημείο μηδέν είναι πλέον το
`0000_production_baseline.sql`, που παράχθηκε από το πραγματικό σχήμα της
παραγωγής και επαληθεύτηκε ότι το αναπαράγει ακριβώς.

## Γιατί αποσύρθηκαν

Υπήρχαν **δύο ανεξάρτητα συστήματα migrations**: τα versioned αρχεία του repo
(που έστησαν το staging) και το ιστορικό του Supabase (που έστησε την παραγωγή).
Είχαν αποκλίνει και προς τις **δύο** κατευθύνσεις:

- το staging είχε 28 πίνακες, η παραγωγή 12,
- η παραγωγή είχε `site_content_updated_idx` που **δεν υπήρχε σε κανένα αρχείο εδώ**.

Τα `0001`, `0003`, `0004`, `0005`, `0006`, `0007`, `0009` περιγράφουν σχήμα που
**υπάρχει ήδη στην παραγωγή**, άρα περιέχεται στο baseline. Δεν χάθηκε τίποτα.

## `0002_site_variants.sql` — αποσύρθηκε ουσιαστικά, όχι μόνο τυπικά

Δημιουργούσε πίνακα `site_variants` και στήλη `clients.selected_layout` που
**δεν υπάρχουν στην παραγωγή και δεν τα αγγίζει κανένας κώδικας**:

```
grep "table('site_variants')"  → 0 αποτελέσματα
grep "selected_layout"         → 0 αποτελέσματα
```

Το ενεργό μοντέλο αποθηκεύει τα designs στον πίνακα **`sites`**, με
`preset` / `url` / `html` / `chosen_variant` (βλ. `db.save_site_variant`,
`db.get_site_variant`, `db.list_site_variants` — τα ονόματα των συναρτήσεων
παραπέμπουν στον παλιό πίνακα και μπερδεύουν, αλλά ο στόχος είναι το `sites`).

Το ότι ένα migration δημιουργούσε επί μήνες πίνακα που κανείς δεν διάβαζε είναι
ακριβώς ο λόγος που χρειαζόταν ενιαία ακολουθία.

## Η σημερινή ακολουθία

```
db/migrations/
  0000_production_baseline.sql   ό,τι υπάρχει σήμερα στην παραγωγή
  0001_agency_kernel.sql         staging-only μέχρι έγκριση για production
```

Το `client_site_claims` **περιέχεται ήδη στο baseline** — μπήκε στην παραγωγή
πριν παραχθεί το αποτύπωμα, οπότε δεν χρειάζεται δικό του migration.

## Τι παραλίγο να χαθεί

Το `0009` όριζε και τη **function** `claim_client_site()`. Το πρώτο baseline βγήκε
χωρίς αυτήν, γιατί το αποτύπωμα μετρούσε μόνο πίνακες/περιορισμούς/ευρετήρια/RLS.
Καθαρό staging θα περνούσε κάθε σύγκριση σχήματος και θα έσπαγε στο πρώτο claim.

Το `scripts/schema_snapshot.py` μετράει πλέον functions και triggers (αγνοώντας
αυτές των extensions, που στο Supabase ζουν σε άλλο schema). Ό,τι δεν μετριέται,
αποκλίνει.
