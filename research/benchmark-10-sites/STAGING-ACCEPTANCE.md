**Πελάτης:** ένας συνθετικός, `ACCEPTANCE Υδραυλικά Δοκιμής`, διαγραμμένος στο τέλος.

**Αλυσίδα υπό δοκιμή:** πραγματικό FastAPI (`src.main:app`, `VITRINA_ENV=staging`)

συμπεριφορά των εικόνων και όχι η επιλογή theme.

## Οπτική κρίση

**Κατάσταση 2** — πλήρες, δυνατό site τεχνίτη: hero με φόρμα προσφοράς, τρία
σενάρια, τέσσερις υπηρεσίες, «ΔΟΥΛΕΙΕΣ ΜΑΣ» με τέσσερις πραγματικές φωτογραφίες,
κίτρινη ζώνη κλήσης, χάρτης. Θα το πουλούσα.

**Κατάσταση 3** — δύο φωτογραφίες αντί τεσσάρων. Δεν φαίνεται «λειψό»: τα δύο
πλακίδια είναι μεγάλα και σκόπιμα.

**Κατάσταση 4** — η κρίσιμη. Η ενότητα «Δουλειές μας» **εξαφανίζεται ολόκληρη**
αντί να μείνει κενή. Η σελίδα ρέει hero → σενάρια → υπηρεσίες → σκούρα ζώνη →
CTA → χάρτης, και είναι **2691px αντί 3193px**: πιο σφιχτή, όχι πιο άδεια. Στα
390px η ταυτότητα και το τηλέφωνο έρχονται πριν τη φόρμα.

### Μία επιφύλαξη που καταγράφω αντί να την παρακάμψω

Στην κατάσταση 4 **το hero εξακολουθεί να δείχνει ενδεικτική φωτογραφία με
άνθρωπο**. Το συμβόλαιο το επιτρέπει ρητά (`hero` = ατμόσφαιρα, δέχεται
`ILLUSTRATIVE`) και η μορφή είναι έντονα σκιασμένη πίσω από τη φόρμα — δεν
διαβάζεται ως «ο τεχνίτης μας». Παραμένει όμως το μοναδικό σημείο όπου ξένος
άνθρωπος εμφανίζεται σε site χωρίς καμία πραγματική φωτογραφία.

Δεν το θεωρώ blocker: κανένας τίτλος δεν τον διεκδικεί ως δικό τους. Το σημειώνω
ως επόμενο σφίξιμο — π.χ. σε `real-only` χωρίς πραγματικό υλικό, προτίμηση σε
ενδεικτικό **χωρίς πρόσωπο** ή τυπογραφικό hero.

## Rollout: **A — αυτόματο default για ΝΕΟΥΣ πελάτες**, με έναν όρο

Τα δεδομένα δεν αφήνουν περιθώριο για το «B — opt-in»: κανένας πελάτης δεν θα
ζητήσει «να μη μου βάζετε ξένες φωτογραφίες», γιατί δεν ξέρει ότι συμβαίνει. Το
«C — μόνο εσωτερικά» ήταν σωστό πριν τη μέτρηση· τώρα το χαρακτηριστικό είναι
αποδεδειγμένο.

**Ο όρος:** το `real-only` γίνεται default μόνο για themes με **αποδεδειγμένη
σύνθεση χωρίς φωτογραφίες**. Σήμερα: `signature` (60), `callout` (59),
`clinic-triage` (58). Το `bakery-editorial` (54) και το `marble` (55) δεν την
έχουν ακόμη — μέχρι τότε, νέος πελάτης σε αυτά τα δύο ξεκινά χωρίς πολιτική.

**Υπάρχοντες πελάτες δεν αγγίζονται ποτέ αναδρομικά.** Ένα ζωντανό site δεν
αλλάζει εμφάνιση επειδή αλλάξαμε εμείς πολιτική.

## Production migration plan — ΔΕΝ εκτελέστηκε

**Προϋποθέσεις**
1. Έγκρισή σου, ρητά για production.
2. `git status` καθαρό για τα αρχεία που αφορούν — τα 10 CapabilitySystems themes
   του παράλληλου agent είναι ακόμη uncommitted· το migration δεν τα αφορά, αλλά
   το deploy του `sites/` τα αφορά.
3. Backup/snapshot της production βάσης πριν από οτιδήποτε.

**Βήματα**

```bash
# 1. Τι πρόκειται να τρέξει — χωρίς να τρέξει
VITRINA_ENV=production python scripts/migrate.py --status

# 2. Εφαρμογή (απαιτεί ρητό flag· χωρίς αυτό ο runner αρνείται)
VITRINA_ENV=production python scripts/migrate.py --apply --confirm-production

# 3. Επαλήθευση σχήματος και συμβολαίου — read-only checks
VITRINA_ENV=production python scripts/migrate.py --status
```

**Το `verify_media_semantics.py` ΔΕΝ τρέχει σε production**: δημιουργεί και
διαγράφει πελάτες. Για production θέλει read-only παραλλαγή που ελέγχει μόνο
`information_schema` και μετράει πόσοι πελάτες έχουν `media_policy` (πρέπει: 0).

**Τι αλλάζει στην παραγωγή αμέσως μετά:** τίποτα ορατό. Δύο στήλες με `NULL`
default, ένα index, και backfill `media_class='REAL_BUSINESS'` σε υπάρχουσες
φωτογραφίες. Κανένα site δεν αλλάζει εμφάνιση όσο κανένας πελάτης δεν έχει
`media_policy`.

**Rollback:** το migration είναι expand-only. Επαναφορά = `ALTER TABLE … DROP
COLUMN media_class / media_policy` (δεν χάνεται δεδομένο πελάτη), ή απλώς αφήνεις
τις στήλες κενές — ο παλιός κώδικας τις αγνοεί.

**Πρώτος πραγματικός πελάτης:** μετά το migration, ενεργοποίηση `real-only` σε
**έναν** πελάτη με δικές του φωτογραφίες, οπτικός έλεγχος, και μετά η πολιτική
του default για νέους.
