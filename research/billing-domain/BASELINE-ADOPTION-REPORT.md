# Υιοθέτηση baseline — η διαδρομή της παραγωγής

**Ημερομηνία:** 2026-09-05
**Η παραγωγή παρέμεινε ΜΟΝΟ ΓΙΑ ΑΝΑΓΝΩΣΗ. Κανένα deploy. Κανένα push.
Καμία εγγραφή στο ιστορικό migrations της παραγωγής. Το 0000 δεν πειράχτηκε.**

---

## Το πρόβλημα, σε μία παράγραφο

Η παραγωγή έχει τους πίνακες που περιγράφει το `0000` αλλά δεν έχει
`schema_migrations`. Το πρώτο `--apply` θα εκτελούσε το `0000` πάνω τους και θα
σταματούσε με `multiple primary keys for table "clients"`: το αρχείο τυλίγει
κάθε περιορισμό σε `EXCEPTION WHEN duplicate_object`, αλλά η PostgreSQL ελέγχει
«δεύτερο primary key» **πριν** από τη σύγκρουση ονόματος και ρίχνει
`invalid_table_definition` (42P16), που δεν πιάνεται.

Η λύση δεν είναι να πειραχτεί το `0000`. Είναι να μπορεί κανείς να **δηλώσει**
ότι το baseline υπάρχει — αφού πρώτα **αποδειχθεί**.

---

## 1. Ο μηχανισμός

```
python scripts/migrate.py --adopt-baseline 0000
```

Σειρά ελέγχων, με **fail-closed** σε κάθε βήμα:

| # | έλεγχος | αν αποτύχει |
|---|---|---|
| 1 | η έκδοση είναι το εγκεκριμένο baseline (`0000`) | άρνηση — κανένα άλλο migration δεν υιοθετείται ποτέ |
| 2 | υπάρχει `db/baseline_fingerprint.json` | άρνηση |
| 3 | το αποτύπωμα αντιστοιχεί στο **σημερινό** `0000` (checksum) | άρνηση |
| 4 | το `0000` δεν είναι ήδη καταγεγραμμένο | άρνηση |
| 5 | το `schema_migrations` δεν έχει άλλες εγγραφές χωρίς baseline | άρνηση — ασυνεπής κατάσταση, θέλει άνθρωπο |
| 6 | **η βάση ικανοποιεί το αποτύπωμα** | άρνηση, με λίστα του τι λείπει |
| 7 | — | δημιουργία `schema_migrations` + **μία** εγγραφή |

Το `schema_migrations` **δημιουργείται μόνο στο βήμα 7**. Μια αποτυχημένη
προσπάθεια δεν αφήνει πίσω άδειο ιστορικό που θα έμοιαζε με «βάση υπό
διαχείριση».

**Καμία εκτέλεση SQL του migration.** Η υιοθέτηση δηλώνει, δεν χτίζει.

### Γιατί μόνο το 0000

Η υιοθέτηση παρακάμπτει εκτέλεση. Αν επιτρεπόταν για οποιοδήποτε migration, θα
ήταν εργαλείο για να «περάσει» κάτι που δεν έτρεξε ποτέ — δηλαδή σιωπηλή
απόκλιση σχήματος. Το baseline είναι η μοναδική περίπτωση όπου μια βάση
**νόμιμα** προϋπάρχει του συστήματος.

## 2. Το αποτύπωμα

`db/baseline_fingerprint.json`, παραγόμενο από
`scripts/make_baseline_fingerprint.py`.

**Παράγεται εκτελώντας το `0000` σε ΚΕΝΗ βάση** — όχι διαβάζοντας την παραγωγή.
Αν το είχα φτιάξει από την παραγωγή, θα επαλήθευα την παραγωγή με τον εαυτό
της και κάθε λάθος της θα γινόταν αυτομάτως «σωστό».

```
12 πίνακες · 95 στήλες · 12 PK · 4 unique · 12 FK
checksum του 0000: baa936fbea60c179
```

**Τι απαιτεί:** ύπαρξη πίνακα· ύπαρξη στήλης με ίδιο **τύπο** και
**nullability**· primary keys· unique constraints· foreign keys — δηλαδή ό,τι
χρειάζονται τα επόμενα migrations για να τρέξουν.

**Τι ΔΕΝ απαιτεί:** defaults στηλών και μη-μοναδικά index. Μια βάση σε παραγωγή
μπορεί κάλλιστα να έχει αποκτήσει επιπλέον index χωρίς αυτό να εμποδίζει κανένα
migration. Ο έλεγχος είναι **υποσυνόλου**: ό,τι απαιτείται πρέπει να υπάρχει·
ό,τι παραπάνω είναι αποδεκτό και αναφέρεται.

Δύο tests κρατούν το αποτύπωμα ειλικρινές: ότι το checksum του αντιστοιχεί στο
σημερινό `0000`, και ότι περιγράφει **ακριβώς** τις στήλες που χτίζει το `0000`.

---

## 3. Το ομοίωμα της παραγωγής

Χτίζεται από read-only introspection της παραγωγής
(`research/billing-domain/production_shape.json` — **μόνο δομή**, καμία γραμμή
πελάτη, κανένα secret).

Το test `test_shape_matches_production` επαληθεύει ότι το ομοίωμα έχει όντως
όλες τις στήλες και τα primary keys της παραγωγής — δεν το υποθέτει.

Και το `test_baseline_would_fail_if_executed` **αναπαράγει την αιτία**: η
εκτέλεση του `0000` σε αυτή τη βάση ρίχνει `InvalidTableDefinition`.

## 4. Η πλήρης ροή, μετρημένη

Πάνω σε βάση σε σχήμα παραγωγής, με **συνθετικές προϋπάρχουσες γραμμές** σε
`clients`, `site_content`, `sites`, `subscriptions`, `domain_orders`, `posts`:

```
--adopt-baseline 0000  → ✅ ΧΩΡΙΣ εκτέλεση SQL· 12 πίνακες, 95 στήλες,
                            12 PK, 4 unique, 12 FK επαληθεύτηκαν
--status               → ✓ 0000 (υιοθετημένο) · υπόλοιπα εκκρεμούν
--apply                → ✓ 0001…0008 · το 0000 ΔΕΝ εκτελέστηκε
```

### Και η πραγματική διαδρομή της παραγωγής, χωριστά

Οι παραπάνω δοκιμές τρέχουν ως `staging`, όπου το `0001_agency_kernel.sql`
**εφαρμόζεται**. Στην παραγωγή δεν πρέπει — φέρει `-- ENV: staging-only`.
Η διαφορά είναι μία γραμμή στο runbook και δεν έμεινε υπόθεση:
η κλάση `ProductionScope` τρέχει το πραγματικό CLI με `VITRINA_ENV=production`
(και `DATABASE_URL_PRODUCTION` σε **αναλώσιμο container**, ποτέ στην παραγωγή):

```
✓ το --apply ΑΡΝΕΙΤΑΙ χωρίς --confirm-production
✓ το --status σημαίνει το 0001 ως «staging-only»
✓ Εφαρμόστηκαν 7.                    ← το runbook λέει 7· εδώ μετριέται
✓ καταγεγραμμένα: 0000, 0002…0008    ← χωρίς 0001
✓ ο πίνακας agent_registry ΔΕΝ υπάρχει
✓ τα δεδομένα επέζησαν και ο editor δουλεύει
```

### Επαλήθευση μετά

| έλεγχος | αποτέλεσμα |
|---|---|
| κάθε έκδοση καταγεγραμμένη σωστά | ✓ |
| `site_revisions` χωρίς legacy στήλες | ✓ 14 στήλες |
| `editor_commit` / `editor_undo` | ✓ 2/2 |
| `site_content.editor_version` | ✓ `bigint NOT NULL` |
| `service_role` σε κάθε πίνακα | ✓ κανένας χωρίς |
| RLS ενεργό παντού + `site_revisions` | ✓ |
| policies | ✓ 0, όπως στο staging |
| **οι προϋπάρχουσες γραμμές, byte-ίδιες** | ✓ 6/6 |
| **πλήθη γραμμών ανά πίνακα** | ✓ 12/12 αμετάβλητα |
| **ο editor δουλεύει σε πελάτη που υπήρχε ΠΡΙΝ** | ✓ commit + undo, το live site ανέπαφο |

## 5. Fail-closed — 12 επικίνδυνες περιπτώσεις

Κάθε μία επαληθεύει **δύο** πράγματα: ότι η εντολή αρνήθηκε, **και** ότι δεν
δημιουργήθηκε `schema_migrations`.

| περίπτωση | αποτέλεσμα |
|---|---|
| λείπει πίνακας (`brand_profiles`) | ✓ άρνηση, ονομάζει τον πίνακα |
| λείπει primary key (`clients_pkey`) | ✓ άρνηση |
| ασύμβατος τύπος στήλης (`clients.name` → varchar) | ✓ άρνηση |
| λείπει στήλη (`clients.phone`) | ✓ άρνηση |
| αλλαγμένη nullability (`clients.city`) | ✓ άρνηση |
| λείπει unique (`domains_domain_key`) | ✓ άρνηση |
| λείπει foreign key (`sites_client_id_fkey`) | ✓ άρνηση |
| εντελώς κενή βάση | ✓ άρνηση |
| υιοθέτηση 0001 / 0003 / 0008 / 9999 | ✓ άρνηση, «ΜΟΝΟ για το 0000» |
| ήδη υιοθετημένο | ✓ άρνηση, καμία διπλή εγγραφή |
| `schema_migrations` μερικώς γεμάτο | ✓ άρνηση, «ασυνεπή κατάσταση» |
| αποτύπωμα ξεπερασμένο έναντι του `0000` | ✓ άρνηση |

## 6. Runbook

`docs/24-PRODUCTION-MIGRATION-RUNBOOK.md` — **δεν έχει εκτελεστεί**.

Α έλεγχοι πριν (μόνο ανάγνωση) · Β αντίγραφο ασφαλείας με **επαλήθευση ότι
διαβάζεται** · Γ επαλήθευση αποτυπώματος · Δ υιοθέτηση · Ε κατάσταση · ΣΤ
εφαρμογή · Ζ επαλήθευση μετά · Η πότε σταματάμε · Θ ανάκτηση.

**Για την ανάκτηση δεν λέγεται ψέμα.** Δεν υπάρχουν down-migrations και δεν
πρέπει να γραφτούν βιαστικά. Το κείμενο ξεχωρίζει τρεις καταστάσεις:

- **πριν** την υιοθέτηση ή **άρνηση** υιοθέτησης → τίποτα δεν γράφτηκε, καμία
  ανάκτηση·
- **αποτυχία μέσα στο `--apply`** → το migration που απέτυχε έκανε rollback μόνο
  του, τα προηγούμενα έχουν δεσμευτεί· **όχι** επανάληψη «για να περάσει», αλλά
  αναπαραγωγή τοπικά και διόρθωση με **νέο** migration·
- **επαναφορά από αντίγραφο** μόνο για χαμένα δεδομένα, ανεξήγητη κατάσταση ή
  βλάβη που δεν εντοπίζεται — και με ρητή προειδοποίηση ότι το PITR **σβήνει
  κάθε εγγραφή πελάτη μετά το `T0`**.

## 8. Τι ξέρουμε ότι δεν ξέρουμε

- **Ο έλεγχος έγινε σε ομοίωμα, όχι στην παραγωγή.** Το ομοίωμα επαληθεύτηκε
  έναντι read-only αποτυπώματος της 2026-08-30. Αν η παραγωγή άλλαξε από τότε,
  το βήμα Γ θα το πιάσει — γι' αυτό υπάρχει.
- **Η σύνδεση MCP στην παραγωγή έπεσε** μετά την αποτύπωση. Νέα ανάγνωση δεν
  ήταν δυνατή· το βήμα Γ του runbook την κάνει ούτως ή άλλως πριν από κάθε
  εγγραφή.
- **Το `0000` παραμένει μη επαναλήψιμο.** Δεν διορθώθηκε — τεκμηριώνεται και
  κλειδώνεται με test. Η υιοθέτηση το κάνει άνευ σημασίας για την παραγωγή,
  αλλά το σχόλιό του («Ασφαλές να ξανατρέξει») εξακολουθεί να είναι λάθος.
- **Το checksum του `0003` μένει ασυμφιλίωτο στο staging**, επίτηδες: το
  staging κρατά πραγματικά δύο legacy στήλες που το σημερινό `0003` δεν φτιάχνει.
  Η προειδοποίηση είναι αληθινή.
