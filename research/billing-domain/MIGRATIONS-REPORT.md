**Καμία εγγραφή στην παραγωγή. Κανένα deploy. Κανένα push. Κανένα ιστορικό migration δεν ξαναγράφτηκε.**

## 1. Τι ακριβώς άλλαξε στο 0003

Το `schema_migrations` του staging κρατά checksum ανά αρχείο:

| έκδοση | καταγεγραμμένο | τώρα στο repo | |
|---|---|---|---|
| 0000, 0001, 0002 | — | — | ίδια |
| **0003** | `2a90de9c461a9d82` | `5a604b8d580d59ed` | **ΔΙΑΦΟΡΑ** |
| 0004, 0005, 0006 | — | — | ίδια |

Εφαρμόστηκε **2026-08-25**. Το git δεν βοηθά: **τα 0003-0007 είναι untracked**
(`git ls-files` δείχνει μόνο 0000-0002 και το `legacy/`). Δεν υπάρχει ιστορικό
της αλλαγής — αυτό είναι από μόνο του εύρημα.

Η αλλαγή ανακατασκευάστηκε από τα **αποτελέσματά** της, συγκρίνοντας τον
πίνακα που έφτιαξε το παλιό 0003 (staging) με αυτόν που φτιάχνει το σημερινό:

```
STAGING (παλιό 0003 + 0004) — 16 στήλες
  id, client_id, timestamp, source, message, operations, before_state,
  after_state, publish_status, previous_revision_id, created_at, status,
  version_before, version_after, idempotency_key, undone_revision_id

ΚΑΘΑΡΗ (σημερινό 0003)      — 14 στήλες
  id, client_id, previous_revision_id, created_at, source, message,
  operations, before_state, after_state, status, version_before,
  version_after, idempotency_key, undone_revision_id
```

**Το 0003 ξαναγράφτηκε από «πίνακας τεκμηρίων» σε «ατομικός editor».** Το παλιό
δημιουργούσε `timestamp` και `publish_status`· το σημερινό φτιάχνει κατευθείαν
την τελική μορφή και δεν τα δημιουργεί.

## 2. Γιατί αυτό σπάει κάθε καθαρή εγκατάσταση

Το 0004 γράφτηκε για να **αναβαθμίσει** τον παλιό πίνακα. Η πρώτη του γραμμή το
λέει: *«Upgrade the legacy 0003 editor evidence table»*. Και διαβάζει τη στήλη
που το σημερινό 0003 δεν φτιάχνει πια:

```sql
UPDATE public.site_revisions
SET created_at = COALESCE(created_at, "timestamp", now()),
```

Μετρημένο, σε **πραγματικά καθαρή** βάση PostgreSQL 17 (container, 0 πίνακες):

```
✓ 0000_production_baseline.sql
✓ 0001_agency_kernel.sql
✓ 0002_media_semantics.sql
✓ 0003_ai_editor_revisions.sql
✗ 0004_ai_editor_atomic_upgrade.sql
    column "timestamp" does not exist
    LINE 20: SET created_at = COALESCE(created_at, "timestamp", now()),
⛔ Σταμάτησα. Οι επόμενες δεν έτρεξαν.
```

Αναπαράχθηκε **δύο φορές**, σε δύο ανεξάρτητα χτισίματα από το μηδέν.

### Γιατί δεν το είχε πιάσει κανείς

Το `scripts/verify_editing_engine.py` υπάρχει ακριβώς γι' αυτό — αλλά εφαρμόζει
**μόνο 0000 και 0003**. Δεν εκτελεί ποτέ την ακολουθία 0003 → 0004 → 0005,
δηλαδή ακριβώς το σημείο που σπάει. Περνούσε πράσινο σε μια κατάσταση που δεν
υπάρχει σε καμία πραγματική βάση.

### Απαντήσεις στα ερωτήματα

- **Το 0004/0005 συμφιλιώνουν τη διαφορά;** Για βάσεις με το **παλιό** 0003, ναι:
  το 0004 ξαναγράφει στήλες, περιορισμούς, index, RLS, δικαιώματα και **και τις
  δύο** συναρτήσεις με `CREATE OR REPLACE`. Για βάσεις με το **νέο** 0003, όχι —
  το 0004 δεν προλαβαίνει να τρέξει.
- **Καθαρή βάση φτάνει στο ίδιο σχήμα με το staging;** Όχι, γιατί δεν φτάνει
  καθόλου. Με τη διόρθωση (§5), φτάνει σε **λειτουργικά ισοδύναμο** (§4).
- **Θα φτάσει η παραγωγή με ασφάλεια;** **Όχι.**

## 3. Η κατάσταση της παραγωγής — το μεγαλύτερο εύρημα

Έλεγχος **μόνο για ανάγνωση** μέσω του Supabase MCP, το οποίο αποδείχθηκε
συνδεδεμένο στην **ΠΑΡΑΓΩΓΗ** (οι 12 πίνακες ταιριάζουν ακριβώς με το
`db/snapshots/production.json`):

| έλεγχος | παραγωγή |
|---|---|
| `schema_migrations` | **ΔΕΝ ΥΠΑΡΧΕΙ** — το `migrate.py` δεν έχει τρέξει ποτέ εκεί |
| `site_revisions` | δεν υπάρχει |
| `site_content.editor_version` | δεν υπάρχει |
| `editor_commit` / `editor_undo` | δεν υπάρχουν |
| πεδία διαθεσιμότητας του 0006 | δεν υπάρχουν |
| πίνακες | 12 (το staging έχει 27) |

Άρα **η παραγωγή δεν έχει τίποτα από τον AI editor**. Το πρώτο
`migrate.py --apply --confirm-production` θα:

1. δημιουργήσει το `schema_migrations` άδειο,
2. τρέξει το 0000 (no-op — είναι φτιαγμένο με `IF NOT EXISTS` και παρήχθη από
   την ίδια την παραγωγή),
3. παρακάμψει το 0001 (`-- ENV: staging-only`),
4. τρέξει 0002, μετά 0003 — που θα φτιάξει τον πίνακα στη **νέα** μορφή,
5. **σπάσει στο 0004**, ακριβώς όπως η καθαρή βάση.

Η διαδρομή της παραγωγής **είναι** η διαδρομή καθαρής εγκατάστασης για αυτά τα
αντικείμενα. Το μέτρησα και ισχύει.

## 4. Πλήρης σύγκριση σχήματος: καθαρή vs staging

Με τη διόρθωση του §5 εφαρμοσμένη τοπικά, καθαρή βάση από το μηδέν:

| κατηγορία | αποτέλεσμα |
|---|---|
| RLS | ✓ ταυτόσημα |
| policies | ✓ ταυτόσημα (0 και στα δύο) |
| **δικαιώματα πινάκων** | ✓ **42 = 42** (μετά το 0007 — πριν ήταν 28 vs 42) |
| **συναρτήσεις (σώμα, κανονικοποιημένο)** | ✓ **ταυτόσημα** — `editor_commit`, `editor_undo` |
| δικαιώματα συναρτήσεων | ✓ ταυτόσημα |
| στήλες | ✗ staging +2 |
| περιορισμοί | ✗ διαφορετικό όνομα, ίδιος κανόνας |
| index | ✗ staging +1 legacy |

Οι τρεις διαφορές, μία προς μία:

| διαφορά | κρίση |
|---|---|
| staging έχει `site_revisions.timestamp` (NOT NULL, default now()) | **υπολειμματική** — `grep` σε όλο τον κώδικα: **καμία αναφορά** |
| staging έχει `site_revisions.publish_status` (NOT NULL, default 'draft') + το check του | **υπολειμματική** — καμία αναφορά στον κώδικα |
| staging έχει index `idx_site_revisions_client (client_id, "timestamp" DESC)` | index πάνω σε αχρησιμοποίητη στήλη |
| καθαρή έχει `UNIQUE (client_id, idempotency_key)` ως **περιορισμό**· το staging τον ίδιο κανόνα ως **μοναδικό index** (`site_revisions_client_idempotency_key`, από το 0004) | **λειτουργικά ισοδύναμο** — η μοναδικότητα του idempotency επιβάλλεται και στα δύο |

**Κανένα από αυτά δεν αλλάζει συμπεριφορά.** Και οι δύο στήλες έχουν NOT NULL με
default, οπότε τα INSERT του νέου κώδικα δουλεύουν και στο staging.

Δεν δημιουργήθηκε migration για να «ισοπεδώσει» αυτές τις διαφορές: το να
προστεθούν νεκρές στήλες σε καθαρές βάσεις θα ήταν διάδοση σκουπιδιών, και το να
αφαιρεθούν από το staging είναι καταστροφική αλλαγή χωρίς όφελος.

## 5. Τα δύο ευρήματα και τι έγινε για το καθένα

### Α. Δικαιώματα `service_role` — ΔΙΟΡΘΩΘΗΚΕ με νέο migration

Σε καθαρή βάση από τα migrations, **25 από τους 27 πίνακες δεν είχαν κανένα
δικαίωμα για τον `service_role`**:

```
χωρίς δικαιώματα: clients, sites, site_content, domains, domain_orders,
  subscriptions, posts, brand_positions… (25)
με δικαιώματα   : site_revisions, client_site_claims  (μόνο όσα έχουν ρητό GRANT)
```

Το API συνδέεται **ως** `service_role`. Σε τέτοια βάση δεν διαβάζει ούτε τον
πίνακα `clients` — δηλαδή **η ανάκτηση από καταστροφή θα παρέδιδε άχρηστη βάση**.

Δεν φαινόταν επειδή staging και παραγωγή τα έχουν ήδη, από τα default privileges
που βάζει το ίδιο το Supabase όταν στήνεται project. Το
`0000_production_baseline.sql` παρήχθη από **αποτύπωμα σχήματος**, και το
αποτύπωμα δεν περιλάμβανε δικαιώματα.

**`db/migrations/0007_service_role_grants.sql`** — προσθετικό, idempotent.
Επαληθεύτηκε:

| | πριν | μετά |
|---|---|---|
| καθαρή: πίνακες χωρίς `service_role` | 25 | **0** |
| καθαρή: δικαιώματα πινάκων vs staging | 28 vs 42 | **42 = 42** |
| staging: δικαιώματα σε δημόσιους ρόλους | 0 | **0** (αμετάβλητο) |
| staging: δικαιώματα `service_role` | 224 | 224 |

Εφαρμόστηκε στο staging — no-op εκεί, όπως αναμενόταν.

**Τι ΔΕΝ κάνει, επίτηδες:** δεν αφαιρεί τίποτα από `anon`/`authenticated`.
Μετρήθηκε ότι η **παραγωγή έχει 154 τέτοια δικαιώματα** (defaults Supabase) ενώ
το staging κανένα. Ο browser client (`sites/lib/supabase.js`) τα χρησιμοποιεί
μόνο για login — δεν κάνει πουθενά `.from()` — άρα η αφαίρεσή τους *μοιάζει*
ασφαλής. Μοιάζει· δεν αποδείχθηκε. Ένα `REVOKE` 154 δικαιωμάτων στην παραγωγή
είναι συνειδητή απόφαση ασφαλείας, όχι παρενέργεια αρχείου που λέγεται «grants».
**Μένει ως ξεχωριστή εκκρεμότητα.**

### Β. Το 0004 — ΔΕΝ ΔΙΟΡΘΩΘΗΚΕ, χρειάζεται δική σου απόφαση

Αυτό **δεν μπορεί** να λυθεί με νέο migration: το 0004 αποτυγχάνει και σταματά
τον runner **πριν** φτάσει οποιοδήποτε 0007+. Η αρίθμηση είναι τεσσάρων ψηφίων
(`^\d{4}_`), οπότε δεν χωράει αρχείο ανάμεσα στο 0003 και το 0004.

Οι μόνες δυνατότητες είναι:

1. **Να γίνει το 0004 ανεκτικό στη μορφή** — το `UPDATE` να τρέχει μόνο όταν η
   legacy στήλη υπάρχει.
2. Να ξαναγραφτεί το 0003 — **απαγορεύεται ρητά** και θα διπλασίαζε την απόκλιση.

Δεν εφάρμοσα το (1) μόνος μου: το 0004 είναι **ήδη εφαρμοσμένο** στο staging και
η αλλαγή του θα παρήγαγε δεύτερη προειδοποίηση checksum — ακριβώς το πρόβλημα
που ερευνούμε. Είναι δική σου απόφαση.

**Το απέδειξα όμως ότι δουλεύει**, εφαρμόζοντάς το τοπικά στη δοκιμαστική βάση
(`research/billing-domain/prove_0004_fix.py`):

```
✓ 0004 (μπαλωμένο) εφαρμόστηκε σε ΚΑΘΑΡΗ βάση
✓ 0005_editor_stale_error_code.sql
✓ 0006_domain_availability.sql
✓ 0007_service_role_grants.sql
```

Η αλλαγή είναι μόνο στο `UPDATE`: αν υπάρχει η στήλη `timestamp` τρέχει όπως
σήμερα· αν δεν υπάρχει, τρέχει η ίδια εντολή χωρίς αυτήν. Για το staging και
κάθε βάση που το έχει ήδη εφαρμόσει, **η συμπεριφορά είναι πανομοιότυπη** —
δεν ξανατρέχει.

## 6. Δοκιμές του editor στην καθαρή βάση — 15/15

Στη βάση που παράγουν τα migrations ως το τέλος (με τη διόρθωση του §5Β):

```

✓ commit: έκδοση 1 · το περιεχόμενο άλλαξε
✓ idempotency: ίδιο κλειδί → duplicate · μία μόνο αναθεώρηση
✓ stale: απορρίπτεται                 SQLSTATE P0001
✓ stale: P0001 (όχι retryable 40001)  ← το 0005 έφτασε σωστά
✓ undo: επιστροφή στο αρχικό · η έκδοση ΠΡΟΧΩΡΑΕΙ (2)
✓ undo: γράφτηκε στη βάση · κρατήθηκε ΚΑΙ η αρχική αναθεώρηση
```

Και τα σώματα των συναρτήσεων είναι **byte-ταυτόσημα** με του staging (§4).

## 8. Τι έγινε — και τι δεν έγινε

**Έγινε:**
- Καθαρή, αναλώσιμη βάση PostgreSQL 17 σε container· όλα τα migrations από το μηδέν, **δύο φορές**
- Πλήρης σύγκριση σχήματος: στήλες, περιορισμοί, index, RLS, policies, δικαιώματα πινάκων και συναρτήσεων, **σώματα συναρτήσεων**
- 15/15 δοκιμές editor (commit, idempotency, stale, undo, εκδόσεις, απομόνωση δημοσιευμένου, δικαιώματα)
- **Νέο** `0007_service_role_grants.sql` — εφαρμόστηκε σε staging και στην καθαρή
- Ανάγνωση της παραγωγής, **μόνο SELECT**

**Δεν έγινε:**
- Καμία εγγραφή στην παραγωγή, κανένα deploy, κανένα push
- Κανένα ιστορικό migration δεν ξαναγράφτηκε — ούτε το 0003 ούτε το 0004
- Κανένα migration δεν ξανατρέχθηκε σε υπάρχουσα βάση

Καθαρίστηκαν: το container και η αχρησιμοποίητη βάση `vitrina_migtest` που είχε
δημιουργηθεί στον server του staging κατά τη διερεύνηση.

**Σημείωση διαδικασίας:** όταν διόρθωσα το 0007 αφού είχε ήδη εφαρμοστεί στη
δοκιμαστική βάση, **ξανάχτισα τη βάση από το μηδέν** αντί να το ξανατρέξω. Ήταν
η ίδια ακριβώς κατάσταση που ερευνούμε — και ο σωστός χειρισμός της είναι αυτός.
